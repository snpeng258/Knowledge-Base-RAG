## 2. 一句话

**Knowledge-Base-RAG —— Summer-Sum** 是一套轻量内部知识检索工具：把假期期间的会议录音文稿和已解析链接收进同一套索引，用 **CLI + Web UI** 快速定位原文，而不是再造一个大而全的知识平台。

## 3. 要解决的问题

日常会议密、链接碎、群聊多，事后很难回答「当时到底怎么说的、材料在哪」。

具体痛点：

- 信息过载：讨论过「产品力 / 技术力」这类路径，但找不到原始上下文。
- 多媒体碎片化：录音、视频、链接无法按关键词落到具体片段。
- 现有方案偏重：团队内已有更完整的整理平台（万总侧），本项目不做替代，只做**假期项目可用的轻量检索**。

**成功标准（本期）**：能对已入库的会议文稿和链接摘要做检索，结果能回到原文位置，并带一小段上下文。

## 4. 当前共识（可当推进基线）

| 维度 | 现阶段倾向 | 备注 |
| --- | --- | --- |
| 形态 | CLI 核心检索 + Web UI 展示 | 两层解耦，CLI 可不依赖网页 |
| 后端 | RAG（文本检索） | 音视频必须先转写；检索对象是文本 |
| 部署 | 本期 CLI 直连本地库优先；线上 API 随后 | **已细化**：API 是团队共享与 Web 的前提，非 CLI 的前置依赖。CLI 支持本地与 `--remote` 双模式 |
| 数据 | 会议文稿 + 链接解析文本 | **已扩大**：飞书妙记/纪要与群内链接文件纳入；任何人的聊天发言原文仍不做，见 §6.2 |
| 智能 | 检索先行，LLM 后置 | **已细化**：LLM 只出现在写路径（入库提炼）；读路径默认无模型依赖 |
| 组织 | 入库时打标签 | 标签采用受控词表，不完全依赖全文语义匹配 |

## 5. 系统草图

```
会议录音/视频 ──► 转写文本 ──┐
                              ├──► 打标入库 ──► RAG 索引 ──► HTTP API ──┬──► CLI
群内链接 ────────► 本地解析 ──┘                                      ├──► Web UI
重要图片 ────────► OCR/描述（试）                                     └──► AI 问答（可选、后置）
```

分层说明：

| 层 | 职责 | 本期要求 |
| --- | --- | --- |
| 数据层 | 文稿、链接摘要、标签、原始 URL / 媒体引用 | 先手工/半自动入库，不实时爬网页 |
| 索引层 | 文本切分、关键词 + 向量检索（实现可后选） | Demo 可用即可，检索方案可换 |
| 核心层 | 入库、切分、检索、数据访问 | **唯一的业务逻辑所在**；CLI / API / MCP 均为其薄门面 |
| CLI | 本地安装、命令行检索 | 不依赖打开网页也能查；本期主路径 |
| MCP | 把检索能力暴露给 AI Agent | 与 CLI 平权，共享核心层 |
| 接口层 | 搜索、按标签/类型/时间筛选、返回片段与定位信息 | 线上 API，团队共享与 Web 的前提 |
| Web UI | 搜索框、卡片结果、标签筛选、时间轴 | 先功能可用，情绪化 UI 靠后 |
| Agent | 总结、问答、Skills | **独立模块**，核心检索不依赖它 |

**部署倾向**：索引和原文引用最终放服务器，避免每人同步一份语料——这是非技术同事可用的前提。但本期先以 CLI 直连本地库打通功能，API 随后抽出。分层落地细节见 [ADR-001](./adr-001-tech-stack-and-architecture.md) 第 4 节。

## 6. 数据边界

### 6.1 本期纳入

- **会议录音 / 视频文稿**：假期约七八次会议，核心语料。**优先取飞书妙记 / 会议纪要的官方转写产物**——自带说话人与时间戳，无需自建转写链路。
- **外部链接**：群内技术文章、论坛贴等。**入库前本地解析**，生成带标签的摘要，并保留原链接。检索展示解析卡片，点击跳转原文或下载原始媒体。链接来源可以是飞书群消息中分享的 URL（仅提取链接本身，见 §6.2）。
- **群内共享文件**：通过飞书官方 API 下载的文档与附件。
- **重要图片**：可尝试 OCR 或描述性解析，作为补充，不作为 Demo 门槛。

### 6.2 本期明确不做

| 排除项 | 原因 |
| --- | --- |
| **任何人的聊天发言原文入库** | 同事发言的权属不在项目方，无法单方面授权收录；且群聊闲聊对检索价值极低 |
| 微信聊天记录 | 无官方授权通道，导出依赖破解，封号与合规风险高 |
| 破解 / 逆向 / 非官方导出 | 任何平台一律禁止，无例外 |
| 实时网页爬取 | 改为入库前解析；检索时不再现爬 |
| 替代现有整理平台 | 本项目只覆盖假期项目的轻量检索 |
| 把 LLM 做成检索前提 | 无模型时，关键词 + 标签检索仍须可用 |

**2026-08-21 边界修订**：原条目「微信 / 飞书聊天记录」整体排除，理由是「导出依赖破解或非官方通道」。现区分通道性质——飞书官方 OpenAPI 配合本人 OAuth 授权（`lark-cli`）不属于破解或非官方导出，因此**允许**通过该通道读取妙记 / 纪要，以及提取群消息中分享的链接与文件。但**发言原文仍不入库**，理由已改为权属而非技术风险，见 [ADR-001 §8](./adr-001-tech-stack-and-architecture.md#8-语料边界变更)。

解析策略补充：不在查询时抓取网页；解析文本与原始链接关联存储。

## 7. 交互方向（Web，非视觉终稿）

- 首页以搜索框为主，接近搜索引擎，而不是后台表格。
- 筛选：类型标签（会议 / 链接 / 视频 / 图片）+ 时间轴（按假期日期回溯）。
- 结果：卡片式。不同类型用不同卡片；点击进详情、原文或原链接。
- 检索结果必须能**落到原文位置**，并给出上下文预览。
- 参考过往「统一认证 / 回忆杀」类站点的情绪价值，但**本期优先级是能查到**。

CLI 侧对应能力：`search`、按 tag/date 过滤、打印片段与来源路径/URL。具体命令名实现时再定。

## 8. 假期结束前的 MVP

只验证「能进、能查、能回原文」，不验证平台化。

**必须有**

1. 会议文稿导入（至少一批假期会议）。
2. 链接解析文本导入（带原 URL 与标签）。
3. 统一检索：返回标题、类型、时间、片段、来源定位。
4. CLI 可查。
5. Web 有搜索框 + 结果卡片。
6. 线上能访问（哪怕是最小部署）。

**可以没有**

- AI 总结 / 多轮问答
- 精致时间轴与多媒体播放器
- 图片 OCR 全覆盖
- 账号体系、复杂权限（若内网先用简单鉴权或先不鉴权，实现时再选）
- 聊天记录

**建议的实现顺序**

1. 约定入库格式（文稿、链接摘要、tag、时间、source）。
2. 先做可替换的检索（关键词即可，向量随后加上）。
3. 抽出 API。
4. CLI 打通。
5. Web 最小搜索页。
6. 部署。

## 9. 拍板状态

### 9.1 已于 2026-08-21 拍板（详见 [ADR-001](./adr-001-tech-stack-and-architecture.md)）

| 原未决项 | 结论 |
| --- | --- |
| 检索实现：先全文还是直接 embedding；向量库选型 | 三层递进（全文+标签 → 向量 → 重排），接口可替换；向量用 PostgreSQL + pgvector，不引入独立向量库 |
| CLI 是本地建索引，还是只调线上 API | 双模式：本地直连 Postgres，`--remote` 走 API |
| 转写工具链由谁跑、文稿格式 | 用飞书妙记 / 纪要的官方转写产物，自带说话人与时间戳 |
| Web 与 CLI 是 monorepo 还是分目录 | pnpm workspace monorepo，核心逻辑独立成 `packages/core` |
| 语言与运行时（原未列出） | TypeScript + Node.js，strict |

### 9.2 仍未拍板（不要在实现里提前锁死）

- **第一版 tag 词表的具体内容**。词表机制已定（受控词表 + 待确认队列），但词条本身要看真实语料才能定。
- **原始媒体（音频/视频）存放**：对象存储、网盘还是只存链接。当前策略是只存链接与飞书引用。
- **内网访问方式**：开放链接、Basic Auth、还是已有统一认证。API 要给团队用时必须决策。
- **部署平台**。
- **Web UI 框架**。选了 TypeScript **不等于**默认 Next.js，见 `AGENTS.md` Critical Rules。
- **embedding 模型最终选型与向量维度**。先用 `bge-m3` 验证链路，表结构需记录模型名与维度以支持更换。
