## 2. 提示词正文（复制以下全部内容）

```text
你现在进入无人值守长程执行模式。我不在旁边，你需要自己判断并推进，直到任务列表走完或时间窗结束。

════════ 第一部分：先读什么 ════════

按顺序读完这四份文档，再动手。它们是本项目的事实来源，你的所有实现都要受它们约束：

1. AGENTS.md —— 操作索引与硬规则。特别注意 Shell Environment 一节的中文编码陷阱
2. docs/designs/adr-001-tech-stack-and-architecture.md —— 架构决策。第 6 节是红线，逐条记住
3. docs/plans/plan-loop-engineering.md —— 推进机制、熔断规则、阻塞处置矩阵
4. docs/specs/data-model.md 与 docs/specs/cli-surface.md —— 数据结构与命令面契约

读完后不要复述给我，直接开始干活。

════════ 第二部分：要推进什么 ════════

目标：把 Knowledge-Base-RAG —— Summer-Sum 从零源码推进到「CLI 能入库、能检索、能回原文」。

任务全部在 GitHub issue 里（仓库 snpeng258/Knowledge-Base-RAG），已按依赖排好序。用 gh 读取每个 issue 的完整正文，里面有精确的验收标准。

【第一优先：打通端到端链路】按顺序做，严格串行：

  #7   monorepo 骨架、TypeScript strict、测试机制
  #8   Docker Compose 起 PostgreSQL + pgvector
  #9   数据库迁移机制与第一版 schema
  #10  本地文件入库（切分、偏移量、幂等）
  #11  全文检索与标签过滤
  #12  CLI 的 search / get / tags / doctor 与退出码契约

  ★ #12 完成即里程碑：项目第一次端到端可用。在此之前请优先保证质量，
    宁可慢也不要带着缺陷往下走。

【第二优先：加厚能力】#12 完成后按此顺序，遇阻可跳：

  #13  检索评测集与基准线
  #14  飞书妙记与会议纪要接入        （与 #15 独立，可任选先后）

对应的父 epic 是 #1~#6，需要整体背景时去读它们。

════════ 第三部分：怎么推进（每个 issue 一个 loop）════════

对每一个 issue，执行以下四个阶段：

【阶段 1 · 侦察】
派一个 sub-agent 去摸清现状，让它回报：
  - 当前代码的实际状态（不是猜测）
  - 本 issue 涉及的范围与已有可复用实现
  - issue 描述与代码现状之间的差异
不要自己边写边摸——摸索会污染你的上下文，且容易半路发现方向错了。

【阶段 2 · 实现】
基于侦察结果做深度分析，然后实现。实现期间反复对照 ADR-001 第 6 节红线。

【阶段 3 · 双路验证】
同时并行派出两个 sub-agent，且不要告诉任一方另一方的存在或结论：
  - 端到端测试 agent：真实执行 issue 里的每一条验收命令，逐条核对实际输出
  - 代码审查 agent：按 docs/conventions/code-review.md 与 ADR-001 红线逐项审查

【阶段 4 · 裁决】
收到两份报告后自己做判断，不要无脑照做。把每条意见归类：
  - 真实缺陷 → 修，计入熔断轮次
  - 超出本 issue 范围的改进建议 → 不修，记进 issue comment 或另开 issue
  - 与 ADR-001 冲突的建议 → 不修，以 ADR 为准

通过后：commit（Conventional Commits 格式），然后进入下一个 issue。
每个 loop 结束必须单独 commit，不要把多个 loop 堆成一个大提交。
【是否 push 由我在启动时指定；未明确授权则只 commit 不 push】

════════ 第四部分：遇到阻塞怎么办（重要）════════

核心原则：技术问题你自己想办法，决策问题一律不许自己拍。

按类型对照处置：

▸ 环境类（容器起不来、端口占用、模型没拉、Ollama 没启动、编码问题）
  → 自己修。有明确修复路径就直接修（换端口、重启服务、改用 CPU 镜像、给脚本加 BOM）
  → 修不好就降级或跳过，并在 issue comment 记录你试过什么

▸ 外部依赖类（飞书 token 过期、目标网站反爬、网络超时）
  → 记录并跳过。不要反复重试消耗时间窗
  → 在 issue comment 写明需要人工介入的具体事项

▸ 实现类（测试失败、类型错误、逻辑缺陷）
  → 在熔断轮次内修（见下）

▸ 依赖类（前置 issue 没完成）
  → 跳过，去做列表里下一个依赖已满足的 issue

▸ 范围类（issue 描述与代码现状不符、范围需要调整）
  → 收窄到你能完成的部分并交付，把差异写进 issue comment
  → 不要擅自扩大范围

▸ 决策类（想换框架、想改架构、想改产品边界、想装 ADR/spec 没提到的重要依赖）
  → 绝对不要自己决定。写进 issue comment 并跳过该 issue
  → 这是 AGENTS.md 的硬规则，没有例外

两条心法：
  · 降级优于阻塞 —— 能用更笨的实现先通链路就先通
  · 跳过不是失败 —— 一次跳过换来后面多个 loop 的推进，总产出更高。
    反复卡在同一个 issue 上是最差的结果

════════ 第五部分：熔断 ════════

单个 issue 最多 2 轮修复。第 2 轮后验证仍不过：
  1. 停止改这个 issue
  2. 把当前状态、失败原因、试过的方案写进 issue comment
  3. 给 issue 打 blocked 标签
  4. 有部分可用成果就提交它；如果改动让链路变坏了，回滚到本 loop 开始前
  5. 去做下一个依赖已满足的 issue

════════ 第六部分：绝对不许做的事 ════════

违反任一条就停下来，不要绕过：

  1. 不 force push，不做破坏性 git 操作
  2. 不改 ADR-001 的架构决策。觉得决策有问题就记录，不要改文档再照新决策实现
  3. 不把任何人的聊天发言原文入库（ADR-001 第 8 节，官方 API 也不行）
  4. 不提交密钥、.env、真实语料、大于 25 MB 的文件
  5. 不删文件，不新增 ADR 没规划的顶层目录
  6. 不用忽略规则糊过 typecheck / test
  7. 不实现聊天记录的破解或非官方导出
  8. 不选定 Web UI 框架或部署平台（仍未决策）

════════ 第七部分：收尾 ════════

时间窗结束或任务走完时，在 docs/updates/ 写一份复盘，包含：
  - 完成了哪些 issue（编号 + 一句话结果）
  - 跳过了哪些，各自原因
  - 哪些事项需要我人工介入决策
  - 推进机制本身有什么该改的

现在开始。从 #7 起。
```

## 3. 复盘与迭代

每次执行后回到本文，根据实际情况调整：

| 观察到的问题 | 调整方向 |
|---|---|
| 反复卡在同一类阻塞 | 在第四部分补充该类型的具体处置手法 |
| 熔断轮次不合适 | 调整第五部分的轮次上限 |
| sub-agent 侦察产出低质量信息 | 收窄第三部分阶段 1 对回报内容的要求 |
| 越权做了决策 | 在第六部分补充具体禁止项，措辞要具体到可判断 |
| issue 验收标准无法机械判断 | 回去改 issue，而不是放宽提示词 |

修订本文时更新 Updated 日期。复盘记录放 `docs/updates/`。
