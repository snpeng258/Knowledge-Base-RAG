## 1. 使用方式

### 1.1 前置检查

```powershell
docker info
ollama ps ; ollama list
lark-cli auth status
gh auth status
git status --short
git branch --show-current
```

**这一步的失败必须现在修，因为 agent 被禁止改系统配置。** 尤其是 Docker 守护进程——它挂了，#8 到#12 全线坍塌。

同时确认：Windows 电源计划不休眠、Docker Desktop 不自动更新重启、磁盘剩余空间足够（TEI 镜像与模型合计约 5 GB）。

**飞书授权有时效**——refresh token 到 2026-08-26。若今晚会跑到 #14，先 `lark-cli auth login` 刷新。

### 1.2 确认起始分支

架构文档目前在 [PR #23](https://github.com/snpeng258/Knowledge-Base-RAG/pull/23) 上。**先把它合进 `main`**，否则 agent 从 `main` 切出的分支里没有 ADR 与 spec，它会读不到自己的行动约束。

合并后：

```powershell
git checkout main ; git pull ; git checkout -b night/2026-08-21
```

今晚所有工作都在这条夜间分支上线性推进，不碰 `main`。

### 1.3 发出提示词

把第 2 节整段复制发出。**不需要再补充任何授权说明**——push 授权、阻塞处置、终止条件都已经写在里面了。

## 2. 提示词正文（复制以下全部内容）

```text
你进入无人值守长程执行模式。我已经去睡了，整晚不会回复你。

这一点决定了你的全部行为方式：你没有提问这个选项。任何时候你想问我什么，
把问题写进 issue comment，然后按你自己的判断继续往下走。等我回复等于整晚停摆。

项目进度很紧。今晚的成功标准是「尽可能多的任务到达终态」，
不是「每个任务都完美」。反复打磨一个任务是最差的结果。

════════ 第一部分：先读什么 ════════

按顺序读完，再动手。这些是本项目的事实来源，你的实现要受它们约束：

1. AGENTS.md —— 操作索引与硬规则。注意 Shell Environment 一节：
   本机是 PowerShell 5.1，中文在控制台显示为乱码但远端数据是正确的。
   看到乱码不要去「修复」，那会把好数据改坏。
   写中文的 issue comment 时用 gh --body-file 传文件，不要用命令行参数传中文。

2. docs/designs/adr-001-tech-stack-and-architecture.md —— 架构决策，第 6 节是红线

3. docs/plans/plan-loop-engineering.md —— 推进机制

4. docs/specs/data-model.md 与 docs/specs/cli-surface.md —— 数据结构与命令面契约

读完直接开始干活，不要复述给我。

════════ 第二部分：要推进什么 ════════

目标：把这个项目从零源码推进到「CLI 能入库、能检索、能回到原文」。

任务在 GitHub issue 里（仓库 snpeng258/Knowledge-Base-RAG），已按依赖排序。
用 gh 读每个 issue 的完整正文，验收标准都在里面。

【关键路径 —— 严格串行，值得多花时间】

  #7   monorepo 骨架、TypeScript strict、测试机制
  #8   Docker Compose 起 PostgreSQL + pgvector
  #9   数据库迁移机制与第一版 schema
  #10  本地文件入库（切分、偏移量、幂等）
  #11  全文检索与标签过滤
  #12  CLI 的 search / get / tags / doctor 与退出码契约

  这六个是地基，后面十个全部依赖它们。跳过其中任何一个，
  代价是后面多个任务连环报废。所以在这六个上你有更多修复轮次（见第六部分），
  也应该更耐心。

  ★ #12 完成即里程碑：项目第一次端到端可用。

【加厚层 —— 遇阻可快速跳过】

  #13  检索评测集与基准线
  #14  飞书妙记与会议纪要接入        （与 #15 独立）
  #15  链接抓取、正文抽取与失败队列
  #16  LLM provider 抽象与 Ollama 提炼
  #17  受控标签词表与自动打标        （依赖 #16）
  #18  TEI 容器接入与向量灌入
  #19  混合检索与降级保证            （依赖 #18）
  #20  重排接入与评测结论            （依赖 #19）
  #21  MCP server
  #22  HTTP API 与 CLI 远程模式

  这些任务失败只意味着「某项能力还没加厚」，不影响已有成果。
  卡住就跳，不要恋战。

父 epic 是 #1~#6，需要整体背景时去读。

════════ 第三部分：怎么推进（每个 issue 一个 loop）════════

【阶段 1 · 侦察】
派一个 sub-agent 摸清现状，让它回报：
  - 当前代码的实际状态（不是猜测）
  - 本 issue 涉及的范围与已有可复用实现
  - issue 描述与代码现状之间的差异
不要自己边写边摸——摸索会污染你的上下文，且容易半路发现方向错了。

【阶段 2 · 实现】
基于侦察结果做深度分析，然后实现。实现期间反复对照 ADR-001 第 6 节红线。

【阶段 3 · 双路验证】
并行派出两个 sub-agent，不要告诉任一方另一方的存在或结论：
  - 端到端测试 agent：真实执行 issue 里的每一条验收命令，逐条核对实际输出
  - 代码审查 agent：按 docs/conventions/code-review.md 与 ADR-001 红线逐项审查

【阶段 4 · 裁决】
收到两份报告后自己判断，不要无脑照做。把每条意见归类：
  - 真实缺陷 → 修，计入熔断轮次
  - 超出本 issue 范围的改进建议 → 不修，记进 issue comment 或另开 issue
  - 与 ADR-001 冲突的建议 → 不修，以 ADR 为准

【每个 loop 收尾，四件事都要做】
  1. commit（Conventional Commits 格式，一个 loop 一个 commit，不要堆成大提交）
  2. push 到夜间分支 —— 这一点已授权，不用问我。
     推上去我早上能直接从 GitHub 看进度，不必开电脑
  3. 在 issue 上留一条 comment：做了什么、验证结果、遗留什么
  4. 完成的 issue 关掉；跳过的打 blocked 标签

commit message 用英文，避免本机中文编码问题。issue comment 用中文，走 --body-file。

════════ 第四部分：唯一的硬约束 ════════

**禁止执行不可逆的破坏性操作。** 这是今晚唯一会让你必须绕道的限制。

判据：**这个操作出错后，能否靠 git 或重跑恢复？** 不能，就属于禁止范围。
下面是清单，但清单不穷尽——遇到清单外的情况，用上面这条判据自己推断。

▸ Git 历史
  force push（任何形式、任何分支）；对已推送的提交做 rebase 或 amend；
  git reset --hard；git clean -fd；删除任何分支；直接推送 main

▸ 文件系统
  删除或移动任何不是你今晚自己新建的文件与目录；
  覆盖 .env 或已有配置文件的原有内容（追加可以）；
  操作仓库目录之外的任何文件

▸ 数据与容器
  docker compose down -v（-v 会删数据卷）；docker volume rm；docker system prune；
  DROP DATABASE / DROP TABLE / TRUNCATE 针对已有数据；
  删除 pgdata、.ollama、模型缓存

▸ 系统与全局
  全局安装或卸载软件；改 PATH 或系统环境变量；改 git 全局 config；
  卸载重装 Docker / Ollama / Node；碰其他项目的目录

▸ 远程协作
  关闭或删除 issue（做完是 close，不是 delete）；删除 PR；
  改仓库设置或可见性；把任何东西合并进 main

▸ 不可逆泄露（推送后进入历史，无法真正撤回）
  提交密钥、.env、真实语料、大于 25 MB 的文件

**需要「回滚」时怎么办：** 用 git stash push -u 把改动存起来，
记下 stash 名字写进 issue comment，然后继续。stash 是可恢复的，reset --hard 不是。

════════ 第五部分：遇到阻塞怎么办 ════════

三步，按顺序：**自愈 → 绕过 → 继续。** 没有第四步「问我」。

【第一步：自愈】

在下列范围内你可以放手做，不用请示：

  ✓ 改仓库内的任何代码、配置、测试、fixture
  ✓ 重启或重建容器（不带 -v）、改端口、改镜像 tag（GPU 起不来就换 CPU）
  ✓ 装项目内依赖（pnpm add，写进 package.json）
  ✓ ollama pull 拉模型
  ✓ 新建文件、新建分支、commit、push 到夜间分支
  ✓ 向前的数据库迁移（加表、加列、加索引）
  ✓ gh issue comment / label
  ✓ 用更笨但能跑通的实现替代复杂方案

降级优于阻塞。能用笨办法先通链路，就先通，在 comment 里记一句「此处已降级」。

【第二步：绕过】

自愈失败，或者这件事根本不在你权限内，就绕过。绕过分两种：

  ▸ 绕过实现方式 —— 换个做法把 issue 的核心价值交付掉。
    比如正文抽取对某个站点失效，就把它记进失败队列，继续处理其他条目，
    而不是卡在这一个站点上。收窄范围后交付 > 整个 issue 报废。

  ▸ 绕过整个 issue —— 打 blocked 标签，写清楚试过什么、卡在哪、
    需要我做什么，然后走下一个依赖已满足的 issue。

下面这些情况直接走「绕过整个 issue」，不要挣扎：

  · 需要我做决策才能继续（选框架、改架构、改产品边界、
    引入 ADR 没提到的重要依赖）
  · 需要外部凭据或人工介入（飞书重新授权、目标站点要登录）
  · 需要执行第四部分禁止的操作才能完成
  · 只能靠入库聊天发言原文才能完成（ADR-001 §8 禁止，官方 API 也不行）
  · 只能靠 ignore / skip 糊过 typecheck 或 test 才能「通过」
    —— 糊过去等于交付了假成果，比跳过更糟

【第三步：继续】

绕过之后立刻开始下一个 issue。不要总结、不要等、不要确认。

════════ 第六部分：熔断（按重要性分级）════════

  关键路径 #7~#12：单个 issue 最多 4 轮修复
  加厚层 #13~#22：单个 issue 最多 2 轮修复

差别的原因：跳过 #8 会让后面五个 issue 全废，跳过 #20 只是排序没优化。
地基值得多试几轮，加厚层不值得。

超过轮次上限：停止改这个 issue，按第五部分「绕过整个 issue」处理。

【依赖坍塌怎么办 —— 这条很重要】

如果关键路径上某个 issue 最终被绕过（比如 Docker 起不来导致 #8 失败），
不要就此认为整晚结束了。改做那些**不需要该依赖**的部分：

  · 数据库不可用 → 做 #15 的正文抽取纯函数与单测、#16 的 LLM provider
    抽象与接口测试、#7 的工程化完善（lint、CI 配置、测试脚手架）
  · Ollama 不可用 → 做除 #16 #17 之外的一切
  · TEI 不可用 → 做除 #18 #19 #20 之外的一切

判断方式：这个 issue 的验收命令里，有多少条不需要那个挂掉的依赖？
能做的部分就做掉，做不了的部分记进 comment。

【二次机会】

任务列表走完一轮后，如果时间还有，回头重试被 blocked 的 issue，
优先重试关键路径上的。此时环境可能已经因为其他 loop 的副作用而变了，
之前失败的原因可能已经不存在。重试最多一轮。

════════ 第七部分：什么时候才算结束 ════════

**唯一允许的正常结束**：#7~#22 全部到达终态（完成或 blocked），
被 blocked 的关键路径 issue 已重试过一轮，复盘已写完。

**以下都不是结束的理由，遇到它们你要继续跑：**

  ✗ 一个 issue 卡住了                    → 绕过，下一个
  ✗ 不确定某个做法对不对                → 选一个你判断更合理的，记进 comment，继续
  ✗ 想确认需求或让我拍板                → 写进 issue comment，按自己判断继续
  ✗ 觉得已经做了不少了                  → 不是理由，继续
  ✗ 剩下的任务看起来都不好做            → 按第六部分拆出能做的部分

**同时不要空转**：任务列表走完就写复盘收尾，不要自己发明列表外的新任务，
不要为了「还在跑」而做范围外的重构。完成即可停止，这是终点不是中断。

════════ 第八部分：收尾 ════════

在 docs/updates/ 写一份复盘（文件名带日期），包含：

  - 完成了哪些 issue：编号 + 一句话结果
  - 绕过了哪些：编号 + 卡在哪 + 试过什么 + 需要我做什么
  - 哪里做了降级实现，后续要补回
  - 有没有 stash 待处理，stash 名字是什么
  - 推进机制本身有什么该改的

复盘也要 commit 和 push。

现在开始，从 #7 起。整晚不要问我任何问题。
```

## 3. 复盘与迭代

每次执行后回到本文调整：

| 观察到的问题 | 调整方向 |
|---|---|
| 因为想请示而停下 | 第五/七部分的措辞还不够绝对，补具体场景 |
| 执行了破坏性操作 | 第四部分补进清单，并检查判据是否表述清楚 |
| 关键路径轮次不够 / 浪费 | 调第六部分的分级轮次 |
| 反复卡在同一类阻塞 | 在第五部分自愈白名单里补该类的具体手法 |
| 依赖挂掉后就整晚空转 | 第六部分「依赖坍塌」的替代任务清单写得不够具体 |
| sub-agent 侦察产出低质量信息 | 收窄第三部分阶段 1 对回报内容的要求 |
| 交付了糊过测试的假成果 | 在验收标准里加反向断言，而不是只在提示词里禁止 |
| issue 验收标准无法机械判断 | 回去改 issue，而不是放宽提示词 |

修订本文时更新 Updated 日期。复盘记录放 `docs/updates/`。
